# 월드 입장·퇴장 — Stage 4

상태: 구현, 사용자 코드 리뷰 대기. Stage 5의 JoinAck와 이동·물리·스냅숏 전송은 포함하지 않는다.

## 실행 흐름

1. GameChannelHandler가 연결의 SessionId로 RoomManager.Join을 호출한다.
2. RoomManager가 세션 상태, 방 존재, 기존 소속, 입장 가능 여부를 확인한다.
3. 월드 명령 큐가 입장 예약을 만들고 Join을 넣는다. 성공한 경우에만 방 멤버십을 추가하고 응답한다.
4. GameWorld.Tick이 명령을 소비한다. 유효한 Join이면 PlayerId를 발급하고 PlayerState를 생성한다.
5. 연결 종료 시 기존 ChannelInactive가 세션을 종료 상태로 표시하고 RoomManager.Leave를 호출한다. 퇴장 명령을 넣고 방 소속과 세션 등록을 제거한다.
6. 후속 틱의 Leave 처리에서 플레이어를 제거하고 입장 예약을 해제한다.

JoinRoomResponse.Success는 예약 수락을 뜻한다. 실제 플레이어 생성 완료를 통지하지 않으며, 입장 대기 중 연결이 끊기면 플레이어 생성 없이 정리될 수 있다. 방 멤버 수와 월드 플레이어 수는 명령 처리 전후에 일시적으로 다를 수 있다.

## 클래스와 소유권

| 타입 | 책임 |
| --- | --- |
| PlayerState | PlayerId, SessionId, Position을 담는 불변 값. 외부 조회는 복사된 상태다. |
| WorldAdmission | 한 번의 입장 예약을 식별한다. 연결 세션 참조와 퇴장 표시를 보관하며 재입장에는 새 객체를 사용한다. |
| WorldCommand | Join/Leave 종류와 해당 입장 예약을 담는 불변 명령. |
| WorldCommandQueue | 여러 연결의 요청을 잠금으로 직렬화하고 FIFO, 예약 한도, 중복 퇴장 제거, 종료 상태를 관리한다. |
| GameWorld | 틱에서만 플레이어를 생성·제거하고 상태를 게시한다. 루프 종료 정리도 같은 소유자가 실행한다. |
| RoomManager | 방 멤버십과 월드 예약을 연결한다. 네트워크 스레드에서 플레이어 상태를 직접 수정하지 않는다. |

RoomManager의 멤버십 잠금 안에서 큐에 Join/Leave를 넣어, 같은 세션의 입장·퇴장 순서를 보존한다. 명령 큐 잠금 안에서는 큐와 예약 정보만 변경한다. 월드 소비자는 RoomManager 잠금을 얻지 않으므로 역순 잠금 의존성이 없다. 어느 잠금에서도 소켓 I/O를 수행하지 않는다.

## 용량과 퇴장 보장

- 방마다 기본 입장 한도는 1,024개, 틱당 명령 처리 한도는 128개다. GameWorld의 상수로 정의하며 이번에는 서버 환경변수 옵션을 추가하지 않는다.
- 입장 한도에는 대기 Join, 현재 플레이어, 아직 Leave를 처리하지 않은 퇴장 예약이 모두 포함된다.
- 예약 하나가 큐에 넣을 수 있는 명령은 Join 한 개와 Leave 한 개뿐이다. 동일 예약의 중복 Leave는 큐에 넣지 않는다.
- 따라서 대기 명령 수는 최대 `2 × 입장 한도`이며 기본값은 2,048개다. Join을 받아들일 때부터 Leave를 위한 공간도 확보한 셈이다.
- Join을 소비해도 예약을 해제하지 않는다. Leave를 소비해 플레이어를 제거한 후 슬롯을 돌려준다. 이 때문에 입장·즉시 퇴장 반복으로 대기 큐를 무제한 늘릴 수 없다.
- 모든 명령은 같은 FIFO를 사용한다. 무효가 된 Join도 처리 한도에 포함한다. 큐가 가득 차도 이미 예약한 Leave는 거부하지 않는다.
- 이미 큐에 들어간 Leave 앞으로 새 명령을 끼워 넣지 않는다. 월드가 정상적으로 틱을 진행한다면 해당 Leave는 최대 `ceil(2 × 용량 / 틱당 처리량)`번의 처리 틱 이내에 소비된다. 기본값은 16틱이며, 과부하에서 실제 시간까지 보장하는 것은 아니다.
- 용량 부족이나 서버/월드 종료 시 새 입장은 WorldUnavailable로 거부하며 멤버십과 플레이어를 만들지 않는다. 현재 플레이어의 정상적인 중복 입장은 용량을 더 사용하지 않는다.

## 플레이어와 재입장

- PlayerId는 월드 실행마다 1부터 증가하는 양의 long이며 해당 월드 안에서 재사용하지 않는다. 다른 방 및 새 서버 실행과 전역적으로 유일한 ID는 아니다.
- 생성 시 Position은 Vector3.Zero다. 실제 스폰 정책, 좌표 단위와 이동 규칙은 후속 단계에서 정의한다.
- Join 처리 시 예약의 퇴장 표시 또는 세션의 연결 종료 상태가 있으면 플레이어 생성을 건너뛴다. Join 처리와 연결 종료가 겹치면 잠깐 생성된 플레이어도 뒤따르는 Leave가 제거한다.
- 이미 큐에 들어간 Join 뒤에 Leave, 그 뒤에 재입장 Join이 들어간다. 서로 다른 예약 객체를 사용하므로 오래된 Leave가 새 플레이어를 지우지 않는다.
- PlayerCount와 GetPlayers는 틱 처리 후 게시한 상태를 읽는다. GetPlayers는 배열을 복사하므로 호출자가 배열이나 값 타입 Position을 바꿔도 내부 상태는 변하지 않는다. 틱 번호와 플레이어 배열을 묶은 원자적 네트워크 스냅숏은 아직 제공하지 않는다.

## 종료와 실패

- WorldLoop는 단일 실행 소유권을 얻은 후 try/finally로 실행한다. 중복 RunAsync가 실패해도 이미 실행 중인 월드를 정리하지 않는다.
- 정상 취소, 실행 전 취소, 시간 공급자/월드 연산 실패 모두 finally에서 모든 GameWorld.Shutdown을 호출한다.
- Shutdown은 큐를 닫고 예약과 명령을 버린 뒤 모든 플레이어를 제거하고 빈 상태를 게시한다. 실제 완료 틱 수는 초기화하지 않으며 정리를 새 틱으로 세지 않는다. 종료한 월드는 다시 Tick할 수 없다.
- 이 정리는 일반 틱당 128개 제한과 별개인 종료 처리다. 해당 월드의 입장 한도로 작업량이 제한된다. Stage 4에는 전송할 퇴장 응답이 없으므로 종료할 때 모든 Leave 명령을 하나씩 실행할 필요가 없다.
- GameServer는 종료 진입 시 RoomManager의 입장을 막고 루프를 취소한다. 리스너를 닫고 루프 완료를 관찰한 뒤 연결과 이벤트 루프를 정리한다.
- 루프가 먼저 정리된 뒤 도착한 ChannelInactive는 방 소속·세션을 제거하며, 닫힌 월드 큐에 대한 Leave는 무시된다. 이미 월드의 모든 플레이어가 제거되어 있으므로 잔류 상태가 생기지 않는다.
- 바인딩 실패 등으로 루프 작업이 시작되지 않았어도 GameServer는 취소된 토큰으로 루프를 한 번 실행하여 소유자의 종료 정리를 거친다.

## 프로토콜과 검증

JoinRoomResponse의 결과 코드에 WorldUnavailable=4만 추가한다. 레이아웃과 기존 0–3 값은 유지한다. 이전 클라이언트는 4를 알 수 없으므로 공유 프로토콜을 함께 갱신해야 한다. 정확한 바이트와 의미는 [Protocol.md](Protocol.md)에 정의한다.

WorldAdmissionTests는 실제 틱 전 생성 방지, 중복 입장, 재입장 FIFO, 예약 한도, 큐 포화 중 퇴장, 즉시 연결 종료, 연결 종료·입장·틱 경합, 과거 퇴장 무효화, 취소·실패 시 모든 월드 정리를 검증한다. RoomClientTests는 실제 TCP 요청으로 플레이어가 생성되고 연결 종료 후 제거되는지 확인한다. WorldLoopTests와 기존 연결·프로토콜 테스트도 회귀 검사한다.
