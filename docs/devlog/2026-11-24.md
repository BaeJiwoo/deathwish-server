## 1단계 — 공용 경기장

### 구현

- 구현 계획에 현재 체력바, 서버 처치 기반 킬로그, Tab을 누르는 동안 표시하는 팀별 점수판을 추가했다. 점수판의 항목은 닉네임, K/D/A, 핑(ms)이다. 체력바와 킬로그는 2단계, 점수판과 RTT 측정은 3단계 범위다.
- Blender 5.2.3 LTS로 24 m × 30 m 경기장을 만들었다. 양쪽 스폰 구역, 엄폐물, 중앙 기둥, 측면 통로 2개가 있다. 팀별 스폰 Empty 5개씩과 방향을 버전 2 JSON에 함께 내보낸다.
- 서버는 `SERVER_TDM_ROOM_ID`로 경기장을 선택한다. 생성 JSON을 Bepu 정적 충돌에 사용하고, 스폰 마커 10개 내에서 입장을 예약하며, 입장 응답에 맵 ID 2를 전송한다. 기본 평지와 PhysicsLab의 응답 형식은 유지했다.
- 기존 Unity 점프·레이캐스트에 필요한 서버 입력 메시지와 Core API를 맞췄다. 실제 `deathwish-client` 작업 사본에 공유 DLL, 맵 리소스와 맵 선택 컨트롤러를 설치했다. 기존 Unity 씬과 패키지 매니페스트의 파일 해시는 설치 전후 같았다.

### 검증

- Blender에서 독립적으로 두 번 내보낸 JSON, C# 서버 DLL에 포함된 리소스, 실제 Unity 클라이언트 복사본의 SHA-256이 일치했다. 경기장 경계·엄폐면·측면 통로와 서로 겹치지 않는 스폰 10개를 검증했다. 기존 PhysicsLab의 지형과 경고 표시 검증도 통과했다.
- .NET 10에서 서버와 ConnectionTests, Unity 스크립트 검사 빌드가 경고·오류 없이 통과했다. Windows PowerShell 5.1 Unity 설치 및 재설치 검사가 통과했다.
- 실제 클라이언트를 복제한 테스트 프로젝트에서 Unity 6000.3.11f1 오프라인 Play Mode를 실행했다. 경기장 메시 10개의 화면 표시와 카메라 충돌 메시 참조, 평지 전환, PhysicsLab 미리보기 복원이 통과했다.
- Windows Application Control이 새 서버와 테스트 실행 파일 및 어셈블리 로드를 차단했다. 서버 회귀 테스트 실행, 실시간 Bepu 주행 및 Unity TCP 맵 전환은 확인하지 못했다.

### 남은 작업

- 1단계 리뷰에서 실행이 허용된 로컬 환경으로 서버 회귀 테스트와 Unity 입장·충돌을 확인한다. 이후 2단계 이름 입력과 두 명의 교전을 시작한다.
- 두 저장소의 변경은 로컬 `codex/tdm-poc`에 남겼다. 커밋과 푸시는 수행하지 않았다.

## 2단계 — 닉네임과 교전

- 이름을 검증하는 팀 데스매치 입장 패킷, 참가자·체력 상태와 처치 이벤트를 추가했다. 기존 평지와 PhysicsLab의 입장·이동과 진단 레이캐스트는 기존 경로를 유지한다.
- 서버가 팀을 배정하고 Blender 팀 스폰을 선택한다. 적중당 피해 25, 발사 간격 0.2초, 팀 스폰 리스폰 3초로 정했다. 아군과 사망한 플레이어는 피해를 받을 대상이 아니며, 사망 중 입력도 적용하지 않는다. TPS 카메라 조준점을 서버 플레이어 몸체에서 다시 확인해 엄폐를 통과하는 피해를 막는다.
- Unity에 닉네임 입력, 팀 색상 캡슐과 사각형 총, 상대 이름표, 로컬 체력바와 킬로그를 붙였다. 테스트 콘솔에 닉네임 입장, 방향 사격, 매치 상태 확인을 추가했다.
- .NET 서버·ConnectionTests·테스트 콘솔·Unity 스크립트 빌드와 설치가 통과했다. 프로토콜 검증, 피해·발사 간격·아군·엄폐·사망·리스폰 회귀 시나리오를 추가했다. 이 호스트의 Windows Application Control 때문에 서버 테스트 실행과 Unity 두 클라이언트의 실시간 교전은 검증하지 못했다.
- Unity 6000.3.11f1 오프라인 Play Mode에서 한글 이름 입력·이름표, 팀별 캡슐과 총, 체력바, 킬로그, 사망 입력 차단, 서버 스폰 위치로의 부활 표시를 검증했다. 장면 종료 때 이미 정리된 HUD 오브젝트를 참조하는 오류를 고친 뒤 다시 실행해 통과했다.

## 3단계 — 5대5 매치와 점수판

- 팀당 기본 5명이며 두 팀이 차면 시작한다. `SERVER_TDM_TEAM_SIZE=1`로 1대1 검증도 가능하다. 적 처치마다 팀에 1점을 주고, 10점에서 승리를 확정한다. 경기 중 빈 팀 자리는 교체 입장이 가능하고, 종료 후 전원이 나가면 서버가 점수와 매치 상태를 초기화한다.
- 처치 전 5초 안에 피해를 준 다른 참가자에게 어시스트를 집계한다. 서버가 보낸 토큰을 클라이언트가 회신하면 서버의 모노토닉 시계로 RTT를 측정한다. Tab 점수판은 팀별 닉네임·킬·데스·어시스트·핑을 표시하며 측정 전에는 대시를 쓴다.
- `deathwish-client` 로컬 브랜치에 최종 스크립트, HUD 메타데이터, 공유 DLL과 맵을 동기화했다. 공유 파일은 원본과 해시가 일치하고 Unity 씬과 패키지 매니페스트의 해시는 변경되지 않았다.
- 서버와 회귀 테스트, 테스트 콘솔, Unity 스크립트 빌드가 경고·오류 없이 통과했다. PowerShell 설치·재설치와 Blender 두 맵 검증도 통과했다. Unity 6000.3.11f1 오프라인 Play Mode에서 2단계 교전 화면, 10인 점수판, K/D/A·RTT 표시, 대기·승리 HUD, Tab 닫기와 연결 해제 처리가 통과했다.
- 최종 빌드의 관리형 진입점 DLL을 `dotnet`으로 직접 실행할 수 있었다. 전체 회귀 테스트가 생략 없이 종료 코드 0을 반환했다. 실제 TCP 세션 10개에서 5대5 배정, 대기·시작, RTT 동기화, 피해, 초과 입장 거부와 이탈 후 교체를 확인했다. 인메모리 테스트에서 10점 승리, 어시스트와 리스폰을 확인했다. 테스트 콘솔의 한글 닉네임 입장도 실제 포트에서 성공했다. [로컬 검증 방법](../Testing.md#13-5대5-경기와-점수판-확인)
- Unity 6000.3.11f1 Play Mode 클라이언트 두 개를 실제 1대1 서버에 연결했다. 한글 이름 입장, 대기에서 경기 시작, 양쪽 RTT, 서버 명중과 체력 감소, 두 클라이언트 킬로그·점수, 리스폰 및 이탈을 확인했다. 평지와 PhysicsLab의 실시간 입장과 렌더링도 통과했다.
- Unity Play Mode 클라이언트 두 개와 MockClient Core 8개를 한 서버에 연결해 5대5 한 판을 마쳤다. 양쪽 Unity에 10명 점수판과 RTT가 표시됐고, 첫 처치의 킬로그·K/D/A·점수가 일치했다. Unity 사격 입력으로 처치와 리스폰을 반복한 끝에 두 화면에 레드 팀 10대0 승리가 표시됐다. Unity 배치 검증은 종료 코드 0이었다. 10명이 각각 Unity를 조작하는 실플레이는 이번 검증 범위 밖이다.
- 두 저장소의 변경은 로컬 `codex/tdm-poc`에 있다. 커밋과 푸시는 수행하지 않았다.

## Unity 테스트 화면 캡처

- Unity 2개와 MockClient Core 8개를 실제 TCP 서버에 다시 연결해 한 판을 실행했다. 1600 × 900 PNG로 경기장 전경, 첫 처치 뒤 교전 HUD, Tab 점수판, 레드 팀 10대0 승리 화면을 캡처했다. 경기장 전경에는 테스트 카메라를 사용했다.
- 10명 정원과 실측 RTT, 양쪽 킬로그·점수판, 최종 승리 일치 검사를 다시 통과했다. 캡처는 로컬 출력에 저장했고 게임 소스와 씬은 수정하지 않았다.

## 경기장 물리 검증 확장

- Blender 경기장 동쪽에 16분할 곡면 아치와 폭 1.05 m, 높이 2.2 m의 무난간 외다리를 추가했다. 다리의 오르막·상판·내리막을 하나의 메시로 연결했고, 바닥 착지와 다리 아래 통과를 확인할 공간을 남겼다. 기존 메시 10개와 스폰 10개, 측면 통로를 보존했다.
- Blender 5.2.3 LTS에서 독립적으로 두 번 내보낸 JSON이 바이트 단위로 일치했다. 서버 어셈블리의 내장 리소스와 실제 `deathwish-client` 복사본도 같은 SHA-256을 확인했다. 총 12개 메시, 정점 172개, 삼각형 296개다.
- Bepu 서버 테스트에서 아치 지상 통과, 기둥 접촉, 개구부와 상단 레이 판정, 천장에 막힌 점프와 착지를 확인했다. 외다리 경사로 접합부, 발판 하부 충돌, 가장자리 일부 지지, 측면 추락과 바닥 착지도 통과했다. 10인 TCP 경기·RTT·피해·교체 입장을 포함한 전체 회귀 테스트가 종료 코드 0으로 끝났다.
- Unity 6000.3.11f1 Play Mode에서 JSON과 렌더링·충돌 메시의 정점 및 면 순서가 일치했다. Unity 레이 검사와 실제 1대1 입장·사격·리스폰·이탈 검증이 통과했다. 경기장 전경과 아치·외다리 확대 화면을 1600 × 900으로 캡처했다.
- 서버의 로컬 `codex/tdm-poc`에 Blender 원본·JSON·검증을, 클라이언트의 같은 로컬 브랜치에 공유 JSON을 반영했다.

## 서쪽 블록 점프 코스

- 기본 30 Hz, 중력 9.81 m/s²와 최고 이동 속도 5 m/s로 Bepu 점프를 측정했다. 같은 높이까지 6.167 m를 1.233초에, 0.4 m 높은 착지면까지 5.833 m를 1.167초에 이동했다. 두 경우 모두 발 최고점은 이륙 높이에서 1.804 m였다.
- Blender 경기장 서쪽에 높이 0.75~1.40 m의 발판 5개와 진입·출구 램프를 추가했다. 간격은 2.10, 3.00, 4.00, 4.65 m다. 첫 검증에서 양쪽 벽 가까이에서 평지에 완전히 내려설 여유가 작아 램프 끝을 안쪽으로 옮겼다. 블록 간격과 상판 높이는 유지했다.
- Blender 5.2.3 LTS에서 최종 JSON을 두 번 내보내 일치함을 확인했다. 기존 12개 메시와 스폰 10개가 일치했고, 최종 맵은 19개 메시, 정점 224개, 삼각형 364개다. 서버 내장 리소스와 실제 Unity 클라이언트에도 동일한 JSON을 적용했다.
- Bepu 회귀 테스트에서 램프 진입, 양방향 각각 네 번의 연속 점프 착지, 출구 하강, 점프 없이 틈에 들어갔을 때 바닥 착지를 확인했다. 10인 TCP를 포함한 전체 서버 회귀 테스트가 종료 코드 0으로 끝났다.
- Unity 6000.3.11f1에서 19개 JSON 메시와 화면·충돌 메시 일치, 발판과 램프, 틈 4개 및 끝단 평지의 레이 판정을 확인했다. 실제 1대1 입장·사격·리스폰도 통과했다. 서쪽 코스 전경을 1600 × 900으로 캡처했다.

## 번호별 순찰 연습장

- `SERVER_TRAINING_ROOM_ID`로 연습장 방을 열 수 있다. 첫 입장부터 플레이할 수 있으며 10점 이후에도 점수, 사망과 팀 리스폰을 계속 처리한다. 연습장과 일반 팀 데스매치는 방 번호를 따로 설정한다.
- MockClient에 번호별 `/patrol`, 자동 입장 후 순찰, 번호 변경과 `/stop`을 추가했다. 1번은 중앙 엄폐물, 2번은 동쪽 아치·외다리, 3번은 서쪽 블록 점프 코스다. 콘솔이 서버 움직임 패킷과 점프 패킷을 보내고, 사망 시 새 리스폰 위치 스냅샷을 기다린 뒤 같은 경로의 입구로 돌아간다.
- 서버·콘솔·회귀 테스트를 최종 Debug 빌드에서 컴파일했다. 의존성 복원에서 NuGet 취약성 정보 조회 환경 경고 `NU1900`이 발생했다. 독립 지오메트리 검사에서 기존 스폰 10개 각각에서 세 구역 입구까지 30개 지상 접근 경로를 확인했고, 기존 맵 검증도 통과했다.
- 서버 연습장의 1인 시작과 11점 지속, 실제 TCP에서 이동·사망·복귀 및 경로별 지형 이동을 확인하는 회귀 테스트를 추가했다. Windows Application Control이 새 서버·콘솔·테스트 바이너리의 로드를 차단했다(`0x800711C7`). Debug·Release와 표준 .NET 실행 경로 모두 Windows에서 차단됐다.
- 변경은 로컬 서버 `codex/tdm-poc` 작업 사본에 반영했다. Unity는 기존 맵과 프로토콜로 연습장에 입장한다. [연습장 설정 및 명령](../Testing.md#16-연습장과-mockclient-순찰)

### WSL 로컬 실행과 Unity 접속

- Windows 코드 무결성 로그의 이벤트 3077과 3089에서 Smart App Control 정책 `VerifiedAndReputableDesktop`이 서명되지 않은 `DeathWish.Server.dll`을 차단했음을 확인했다.
- Smart App Control을 켠 상태에서 WSL 2에 Ubuntu 24.04와 .NET SDK `10.0.115`를 설치했다. 순찰 연습장의 현재 소스와 맵을 WSL 전용 계정의 작업 디렉터리에 복사했다. Linux Release 빌드가 경고·오류 없이 끝났으며 전체 서버 회귀 테스트가 종료 코드 0으로 통과했다.
- 실제 TCP에서 10인 팀 데스매치 입장과 RTT, 중앙 순찰 봇의 사망·리스폰·복귀, 동쪽 외다리 횡단, 서쪽 발판 5개 착지를 확인했다.
- WSL의 서버는 `127.0.0.1:17779`에서 수신한다. Windows의 자동 전달이 IPv4 매핑 IPv6 소켓을 잡지 못해 WSL에서 `socat`으로 IPv4 루프백 `127.0.0.1:17780`을 연결했다. 실제 Windows Unity의 `SyncTestScene`에서 이 포트로 3번 연습장에 입장했다. 화면에 `Connected | TeamDeathmatch`, `Players: 4`, `HP 100 / 100`이 표시됐다.
- WSL 서버와 `CoverBot`, `BridgeBot`, `JumpBot`을 실행 상태로 두었다. 세 봇 모두 각자 지정한 순찰 구역에 도착했다. 수동 테스트는 Unity Game 뷰의 `Capture input`에서 이어갈 수 있다.

## 사격 표시와 봇 간 교전

- 사용자 요청에 따라 기존 Unity Play 모드와 연습장 서버, 순찰 봇 3개, 로컬 전달 프로세스를 종료했다.
- 캡슐 옆에 색이 분리된 사각형 총을 장착했다. 입력을 잡은 뒤 좌클릭하거나 누른 채로 사격하면 즉시 섬광과 반동을 표시한다. 벽 때문에 카메라가 캡슐 가까이 밀리면 카메라 쪽 총을 사용한다.
- `ArenaShot`을 요청한 참가자에게 서버의 원점·종점과 빗나감, 지형, 피해 없는 접촉, 피해 적용을 공유한다. Unity가 다른 참가자의 섬광과 궤적, 본인의 명중 결과를 표시한다. 기존 입장과 `RaycastResult` 프레임도 처리하며, 새 이벤트 수신 버퍼는 최근 64개로 제한한다.
- `/patrol 4`는 기존 맵 동쪽 외곽 통로의 팀별 위치로 이동해 반대 팀을 사격한다. 봇이 사망하면 리스폰 위치를 확인하고 같은 구간으로 복귀한다. 기존 1~3번은 순찰을 수행한다.
- WSL .NET 10 Release 전체 회귀가 종료 코드 0으로 통과했다. 10인 TCP, 1~3번 순찰, 4번 봇 3개의 자동 처치·점수·리스폰·교전 복귀와 사격 이벤트의 선택 수신·버퍼·기존 사격 응답 공존을 검증했다. [연습과 테스트 방법](../Testing.md#16-연습장과-mockclient-순찰)
- Unity 스크립트 빌드와 PowerShell 7 설치기 회귀가 통과했다. Windows Unity 6000.3.11f1 배치 Play Mode에서 Unity 클라이언트 2개와 MockClient 8개가 같은 경기를 진행했고, 사각형 무기, 피해 확인, 다른 플레이어 탄 궤적, 킬로그와 10–0 결과를 확인했다. 첫 검사에서 종료 중 이미 해제된 총 오브젝트를 참조하는 오류를 고쳤고, 수정 후 재검사가 종료 코드 0으로 통과했다. Unity 배치 로그에는 에디터 자체 검색 인덱싱과 Burst JIT 로드 메시지가 남았다.
- `deathwish-client` 로컬 작업 사본에 검증한 스크립트, 셰이더와 DLL을 설치했다. 기존 씬과 패키지 매니페스트 해시를 비교했다. 검증에 사용한 복제 Unity 프로세스와 WSL 서버 및 전달 프로세스도 종료했다.

### 봇 교전 수동 테스트 준비

- 검증한 Linux Release 서버를 WSL에서 다시 시작하고 방 3에 `Drill1`–`Drill4`를 `/patrol 4`로 입장시켰다. 봇의 사망과 리스폰 후 복귀를 실제 실행 로그에서 확인했다.
- 열려 있던 Windows Unity의 `SyncTestScene`을 Play 모드로 전환했다. `LocalTester`로 `127.0.0.1:17780`, 방 3에 입장해 참가자 5명과 양 팀의 처치 점수를 확인했다. 수동 조작은 `Capture input`에서 시작한다. 서버, 로컬 전달 및 봇 4개를 실행 상태로 두었다.
- 사용자 요청에 따라 로컬 전달, 봇 4개, 연습장 서버를 종료했다. 대상 프로세스 종료와 월드 루프 정지를 확인했다. Windows 잠금 화면으로 Unity의 Play 모드 전환은 확인할 수 없었다.
- 이후 3번 연습장을 다시 열어 4번 교전 봇 6개를 양 팀에 3개씩, 1·2·3번 순찰 봇을 하나씩 입장시켰다. `LocalTester`로 Windows Unity Play 모드에서 접속해 총 10명과 양 팀 처치 점수를 확인했다. 봇 로그에서 4번의 사망·리스폰 복귀와 1·2·3번의 구역 도착을 확인했다. 서버, 봇 9개와 Unity를 실행 상태로 두었다.

### 오른쪽 총 장착과 어깨 카메라 구도

- 사용자 요청에 따라 연습장 서버, 로컬 전달 및 봇 9개를 종료했다. Unity 에디터는 Play 모드가 꺼진 상태를 확인했다.
- 사각형 총을 캡슐 오른쪽 바깥에 고정하고 본체와 총열을 키웠다. 장착부가 총을 캡슐에 연결한다. 어깨 전환 시에도 총은 캐릭터 오른쪽에 있으며, 카메라가 벽에 많이 당겨질 때는 화면 오른쪽 아래에 표시한다.
- 팀 데스매치와 연습장의 카메라 좌우 위치를 화면 비율에 맞게 조정했다. 기본 오른쪽 어깨에서 열린 공간의 몸통 기준점은 화면 왼쪽에서 약 16% 지점이다. 반대 어깨는 오른쪽으로 배치하며 조준선과 지형 충돌 처리를 유지한다.
- Unity 스크립트 빌드와 실제 클라이언트 설치가 통과했다. 복제 프로젝트의 오프라인 Play 모드에서 4:3, 16:9, 21:9 양쪽 어깨의 몸통 위치·중앙 조준·총 위치와 벽에 막힐 때의 표시를 확인했다. 그래픽 렌더링 검사에서 총이 화면에 표시됐고, 맵·전투 HUD 검증도 통과했다. 검증용 Unity 프로세스를 종료했다.
- 이후 사용자 요청에 따라 WSL 서버와 로컬 전달을 다시 실행했다. Unity 접속 주소 `127.0.0.1:17780`에서 Windows 클라이언트의 Echo 요청과 응답을 확인했다. 2번은 팀 데스매치, 3번은 연습장으로 열었다.

### 경기장 확장과 원통형 캐릭터

- Blender 원본의 바닥과 경계 벽을 조정해 팀 데스매치와 연습장에 사용하는 경기장을 24 m × 30 m에서 32 m × 38 m로 넓혔다. 외곽에 우회 공간이 생겼다. 새 JSON의 내부 메시 14개와 스폰 10개를 이전 JSON과 비교했다. Blender 독립 내보내기 두 번과 Unity 검증 프로젝트에서 JSON 해시가 일치했다.
- Unity는 원통 메시의 실제 바운드를 지름 0.65 m, 높이 1.8 m에 맞추고 바닥을 서버가 보내는 발 위치에 정렬한다. 서버도 같은 치수의 Bepu 원통을 사용한다.
- 오프라인 Unity 렌더링 검사에서 32 m × 38 m 바닥, 새 모서리, 원통 모델, 사각형 총, 아치, 외다리, 점프 코스와 전투 HUD를 확인했다. 별도 WSL 검사에서 새 외벽과 외곽 이동, 아치·외다리 이동, 양방향 연속 네 번의 점프와 바닥 착지가 통과했다.
- 원통 밑단이 경사로 삼각형 접합부에서 걸리거나 튀는 동작을 지지면이 확인되는 경우에 한해 보정했다. WSL Release 전체 회귀가 통과했다. 원통의 측면 반경·평평한 상하단·모서리 바깥 레이, PhysicsLab 경사로 왕복과 벽, 10인 교전, 연습장 순찰 1–4를 확인했다.
- 연결 중인 클라이언트가 없는 것을 확인한 뒤 새 WSL 서버로 교체했다. 실제 Unity 클라이언트에 같은 맵과 모델을 설치했고 장면 및 패키지 매니페스트 해시를 비교했다. Windows `127.0.0.1:17780` Echo 왕복과 MockClient 3번 연습장 입장이 통과했다.
- 사용자 요청에 따라 확장된 3번 연습장에 MockClient 9개를 입장시켰다. 1·2·3번 봇의 구역 도착과 4번 봇의 사망·리스폰 후 복귀를 실행 로그에서 확인했다. 서버와 봇은 실행 상태로 두었다.
