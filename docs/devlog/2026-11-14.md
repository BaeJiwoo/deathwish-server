## 설계 결정

- 방마다 GameWorld를 두고 서버 실행당 WorldLoop 하나가 갱신한다. 모든 방은 같은 레이트를 사용하고 빈 방도 갱신한다.
- 실제 월드 연산 진입점은 동기 Tick(float deltaTime)이다. Stage 3에서는 완료 틱 번호까지 구현하며 플레이어 상태와 게임 로직은 후속 단계다.
- 타임스탬프·주파수·정수 틱 번호를 Int128 중간값으로 비교하여 주기 반올림과 누적 오차를 피한다. 게임 로직에 전달할 delta만 float로 고정한다.
- 보충 묶음은 첫 실행을 포함해 최대 4틱이다. 초과 기한은 건너뛰고 실제 완료 틱 번호를 증가시키지 않는다.
- 대기는 밀리초 단위로 올리고 보충 한도 초과 후에도 최소 1ms 대기한다. 통계 처리 중 다음 기한이 지나가는 매우 높은 레이트에서도 계속 연산하는 루프가 되지 않도록 했다.
- 처리 시간 초과 횟수와 늦게 깨어난 횟수를 구분한다. 완료 횟수는 방별 합계가 아닌 전체 방 갱신 횟수다.
- 하나의 루프는 한 번만 실행할 수 있으며 동시에 시작하려는 호출도 거부한다. 틱 번호는 다른 스레드에서 안전하게 읽도록 게시한다.
- GameServer의 internal 생성자에서 TimeProvider를 주입할 수 있게 하여 실제 서버의 루프 실패와 취소 경합을 검증했다. 공개 생성자는 시스템 시간을 사용한다.
- 취소와 실패가 동시에 발생해도 루프 예외를 관찰한다. 정리 실패가 있어도 다른 자원 정리를 시도하고 실패가 여럿이면 AggregateException으로 보존한다.
- TickRate는 양의 int32를 허용하지만 실제 달성 가능한 레이트를 보장하지 않는다. 설정은 재시작 시 반영한다.

## 검증

- 명세 작성 시에는 문서 링크와 코드 블록 구분자를 확인했으며, 이후 사용자의 구현 요청에 따라 아래 검증까지 수행했다.
- 호스트 기본 SDK는 .NET 8.0.424로 프로젝트의 net10.0 대상을 지원하지 않았다. 초기 빌드 시도에서 assets 미생성과 SDK 대상 버전 오류를 확인했다.
- 공식 Microsoft 배포 경로에서 .NET 10.0.404를 `/tmp/deathwish-dotnet10`에 별도로 준비하고 다운로드 체크섬을 확인했다. 프로젝트 대상 프레임워크와 기본 dotnet 경로는 변경하지 않았다.
- ConnectionTests 및 MockClient.Console 빌드: 모두 경고 0개, 오류 0개.
- 전체 ConnectionTests 실행: 종료 코드 0. 기존 Echo, 프로토콜, 세션, 방 관리, MockClient 및 실제 TCP 회귀 검사를 포함한다.
- 제어 시간 테스트: 첫 틱 대기, 30Hz 300틱을 10초 동안 처리하며 누적 주기 오차가 없는지, 연산 시간을 다음 대기에서 빼는지, 고정 delta, 4틱 보충 제한, 지속 과부하, 통계, 최대 int32 레이트에서도 대기하는지 확인했다.
- 소유권·실패 테스트: 방별 월드 분리, 목록 복사, 방 순서, 중복·동시 루프 시작 거부, 취소 시 전체 방 틱 완료, 실제 시스템 시간에서 실행·종료를 확인했다. 비공개 틱 카운터를 테스트에서만 long.MaxValue로 설정하여 중간 방의 연산 실패 시 뒤 방을 실행하지 않고 전체 완료 틱도 증가하지 않는지 검증했다.
- 실제 GameServer TCP 테스트: 두 클라이언트의 방 입장과 Echo, 연결 중 취소 종료, 루프 실패와 취소 동시 발생 시 원래 예외 보존, 연결 EOF, 포트 재사용, 바인딩 실패 시 루프 미실행을 확인했다.
- 기존 실제 TCP 방 테스트는 종료 후 세션·방 멤버 수가 0임을 직접 검사한다. 새 GameServer 테스트는 내부 지역 레지스트리를 노출하지 않고 소켓 종료와 포트 재사용을 검사한다.
- 별도 실제 실행 파일 검증: 임시 디렉터리의 공개 예시 .env 값으로 3개 방·60Hz 시작, 정확한 Echo 바이트 응답, 14틱 진행, SIGINT(Ctrl+C 신호) 종료 코드 0, 클라이언트 EOF 및 포트 재사용을 확인했다. 사용자 로컬 .env는 읽거나 수정하지 않았다.
- `git diff --check` 통과. 새 파일을 포함한 변경 파일 21개의 후행 공백과 Markdown 상대 링크·코드 블록 구분자를 검사해 통과했다.

## 파일 이동·삭제 점검

- 사용자가 조작 실수 가능성을 알려 Git 상태와 실제 파일 위치를 추가 점검했다.
- 추적 파일의 삭제·이동·이름 변경과 스테이징된 변경은 발견되지 않았다. 추적 파일은 모두 존재하고 모든 프로젝트 참조 경로가 유효했다.
- 수정 파일 13개와 새 파일 8개의 경로는 Stage 3 구현 직후 보고한 상태와 같았다. 새 파일 8개도 모두 의도한 명세·개발 기록·월드·테스트 파일이었다.
- Git 제외 항목은 각 프로젝트의 bin/obj 빌드 산출물이었다. 빌드 경로 밖에 빈 디렉터리도 발견되지 않았다.
- 현재 저장소에서 이동·삭제로 복구할 항목은 발견하지 못했다. 소스 파일을 이동·복원하거나 테스트를 재실행하지 않았으며 점검 결과만 이 기록에 추가했다.
