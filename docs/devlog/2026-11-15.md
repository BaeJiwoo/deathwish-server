## Stage 6 - Server-authoritative movement

### Scope and implementation

- Added MoveInput (type 6): uint32 sequence and float32 X/Z direction. Protocol.md defines exact big-endian bytes, ranges, axes, speed, modular sequence ordering, timeout, client behavior and compatibility.
- Added one synchronized MovementMailbox per WorldAdmission. Newer input replaces the previous value instead of adding world commands. Movement storage is bounded by admission capacity and cannot occupy the reserved Join/Leave queue.
- GameWorld processes lifecycle commands before applying movement once per active player per tick. Maximum speed is 5 m/s on XZ; vectors longer than one are normalized, shorter analog vectors retain magnitude, and Y is unchanged. Only the world owner updates and publishes PlayerState.
- Input expires at monotonic receipt age >=250ms. Duplicate, older and half-range-ambiguous sequences do not refresh age. uint.MaxValue to zero wraps correctly. Expiry preserves sequence history; rejoin resets it through a new admission token.
- Departure closes and clears the input slot immediately, including while Leave waits for its tick budget. Shutdown closes every slot. Pending admissions do not refresh input age when players are created.
- GameServer passes its TimeProvider through RoomManager, Room and WorldCommandQueue to the admission slots for consistent production/test timing.
- MockClient.Core adds SendMoveAsync after JoinAck. Movement and requests share an operation guard; no MoveInput response is expected. Console adds /move x z with automatic sequence increments and /move 0 0 for stopping. It sends a single sample per command, not a continuous stream.

## 설계 및 범위 정리

- 이슈의 기본 흐름을 접속 → 방 입장 예약 → 틱에서 플레이어 생성 → JoinAck → 입력 전송 → 서버 스냅숏 수신으로 정리했다.
- 현재 JoinRoomResponse.Success는 예약 수락이며 PlayerId를 전달하거나 생성 완료를 통지하지 않는다는 점을 명시했다. 서버 내부 GetPlayers 복사본도 네트워크 스냅숏 전송과 구분했다.
- 구현된 기능 체크와 단계별 코드 리뷰 승인을 구분했다. 이번 이슈 수정만으로 Stage 4 완료 체크를 변경하지 않았다.
- Unity 구현은 별도 저장소 작업으로 구분하고, 늦은 입장·새 플레이어 표시·퇴장 제거·서버 이동 결과 표시를 통합 완료 조건으로 남겼다.
- 기존 이슈에서 한 항목에 묶였던 이동, 물리, 애니메이션을 단계별로 구분했다. 점프·중력·충돌·애니메이션 상태 머신과 기존 Idle/Run 표현 목표는 장기 로드맵의 후속 확장으로 명시했다.
- 양자화는 Stage 8, 플랫폼·부하 검증은 Stage 9로 연결했다. UDP, 예측·보정, 지연 보상, 전투·캐릭터 스킬은 초기 동기화 범위 이후 작업으로 구분했다.
- 기존 PoC 참고 링크와 이슈의 열린 상태, 라벨, 담당자, 마일스톤은 유지했다. 새 이슈나 댓글은 만들지 않았다.
