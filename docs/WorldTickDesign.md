# 틱 기반 월드 클래스 명세

상태: Stage 3 구현 및 Linux 검증 완료, 사용자 코드 리뷰 대기. 완료 체크는 리뷰 승인 후 변경한다.

## 1. 범위와 구조

방마다 게임 상태와 연산을 담당하는 `GameWorld`를 하나씩 생성한다. 서버 실행 하나에 `WorldLoop` 하나를 생성하여 모든 월드를 고정 주기로 순차 갱신한다. 모든 방은 같은 서버 틱 레이트를 사용하며 빈 방도 갱신한다.

```text
GameServer.RunAsync
  ├─ ServerOptions → TickRate
  ├─ RoomManager
  │    └─ Room × RoomCount
  │         └─ GameWorld
  └─ WorldLoop → 각 GameWorld.Tick(fixedDeltaTime)
```

이번 단계는 실행 기반과 통계를 만든다. 플레이어 상태, 입장·퇴장 명령 큐, 이동·전투·충돌 로직, 스냅숏, 패킷 변경은 포함하지 않는다. 기존 방 멤버십과 월드의 시뮬레이션 상태는 별개이며, 방 입장이 아직 플레이어 생성을 의미하지 않는다.

## 2. GameWorld — 실제 월드 연산

파일: `src/DeathWish.Server/GameWorld.cs`

| 멤버 | 접근 수준 / 타입 | 계약 |
| --- | --- | --- |
| `GameWorld(int roomId)` | internal 생성자 | 양수 방 ID를 받는다. 잘못된 값은 `ArgumentOutOfRangeException`. 초기 틱 번호는 0이다. |
| `RoomId` | public get / `int` | 소속 방 ID. 생성 이후 바뀌지 않는다. |
| `CurrentTick` | public get / `long` | 성공적으로 완료한 틱 수. 외부 읽기는 안전하게 게시된 값 하나를 반환한다. |
| `Tick(float deltaTime)` | internal / `void` | 초 단위의 유한한 양수 시간 간격을 받아 동기적으로 한 틱을 연산한다. 잘못된 값은 `ArgumentOutOfRangeException`. |

책임과 규칙:

- `Room`이 생성하고 소유한다. 서버를 다시 실행하면 새 인스턴스를 만든다.
- `WorldLoop`만 `Tick`을 호출한다. 내부 게임 상태를 수정하는 주체도 해당 루프 하나로 제한한다.
- `Tick`은 연산 완료 후 `CurrentTick`을 1 증가시킨다. 첫 완료 틱은 1이다.
- 추후 게임 로직은 `Tick` 안에 정해진 순서로 추가한다. Stage 3에서는 틱 번호 갱신까지 구현한다.
- 소켓 I/O, 비동기 대기, 자체 타이머와 스레드를 갖지 않는다.
- `CurrentTick` 읽기가 안전하다는 것은 향후 플레이어 상태 전체를 다른 스레드에서 읽어도 된다는 뜻이 아니다. 복합 상태 조회에는 별도 스냅숏이 필요하다.
- 연산 예외는 호출자에게 전파한다. 실패한 틱의 상태를 롤백하거나 같은 틱을 재시도하지 않고 서버 실행을 중단한다. 틱 번호가 `long.MaxValue`를 넘으면 `OverflowException`으로 중단하여 음수로 순환하지 않는다.

## 3. WorldLoop — 틱 스케줄링

파일: `src/DeathWish.Server/WorldLoop.cs`

| 멤버 | 접근 수준 / 타입 | 계약 |
| --- | --- | --- |
| `WorldLoop(IReadOnlyList<GameWorld> worlds, int tickRate, TimeProvider? timeProvider = null)` | internal 생성자 | 월드 목록을 복사해 고정한다. null 목록·요소, 빈 목록, 중복 방 ID, 0 이하 레이트를 거부한다. 시간 공급자 생략 시 `TimeProvider.System`을 사용한다. |
| `MaxCatchUpTicks` | internal const / `int` | 한 보충 처리 묶음의 최대 실행 횟수. 초기값 4. 정상적으로 실행할 첫 틱도 이 횟수에 포함한다. |
| `TickRate` | internal get / `int` | 초당 목표 틱 수. 실행 중 변경하지 않는다. |
| `FixedDeltaTime` | internal get / `float` | `1f / TickRate`. 모든 월드와 모든 틱에 같은 값을 전달한다. |
| `RunAsync(CancellationToken cancellationToken)` | internal / `Task` | 루프를 실행하고 종료까지 나타내는 작업을 반환한다. 인스턴스당 한 번만 호출할 수 있다. 중복·재실행은 `InvalidOperationException`. |
| `GetStatistics()` | internal / `WorldLoopStatistics` | 같은 시점에 게시된 불변 통계 스냅숏을 반환한다. 실행 중 다른 스레드에서 호출할 수 있다. |

실행 소유권:

- DotNetty 이벤트 루프에서 월드 연산을 실행하지 않는다. `GameServer`가 별도 작업으로 `RunAsync`를 시작하고 반환 작업을 반드시 추적한다.
- 물리적으로 같은 스레드에서 계속 실행될 필요는 없다. 하나의 비동기 제어 흐름이 연산을 직렬 실행한다는 것이 계약이다.
- 방 ID 오름차순으로 모든 월드의 `Tick`을 호출한 것을 서버 루프 한 틱으로 정의한다.
- 방별 연산을 병렬화하거나, 타이머 콜백마다 독립 작업을 시작하지 않는다.
- 방 멤버십 잠금을 잡은 채 월드 연산을 실행하지 않는다.

시간과 지연 처리:

1. 단조 증가 타임스탬프로 경과 시간을 계산한다. 운영체제의 달력 시각을 스케줄 기준으로 사용하지 않는다. 시간 공급자 주입은 지연·취소 검증을 위한 경계다.
2. 시작 시점부터 한 주기가 지난 시각을 첫 실행 예정 시각으로 둔다.
3. 예정 시각까지 남은 시간만 취소 가능한 방식으로 기다린다. 대기가 일찍 끝나면 시간을 다시 확인한다. 바쁜 반복 대기는 사용하지 않는다.
4. 실행 예정 시각에 도달하면 모든 월드를 한 번 갱신한다. 다음 예정 시각은 이전 예정 시각에 고정 주기를 더해서 계산한다.
5. 지연으로 다음 틱도 실행할 시점이면 기다리지 않고 보충하되 한 묶음에서 최대 4틱만 실행한다.
6. 4틱 실행 후에도 밀려 있으면, 현재 시각까지 남아 있는 실행 기한의 틱 수를 계산해 그만큼 예정 시각을 건너뛴다. 다음 예정 시각은 현재보다 미래여야 한다. 건너뛴 틱 수에 고정 주기를 곱한 시간을 `DroppedTime`에 누적한다.
7. 건너뛴 틱은 실제로 연산하지 않으며 월드와 루프의 완료 틱 수를 증가시키지 않는다. 큰 `deltaTime`으로 합쳐 처리하지 않는다.

스케줄 계산은 단조 증가 타임스탬프, 타임스탬프 주파수, 정수 틱 번호를 사용한다. 비교와 나눗셈 중간값은 `Int128`로 계산하여 틱 주기 반올림과 누적 오차를 피한다. 게임 로직에 전달할 때만 고정 `float` 간격을 사용한다. 대기는 밀리초 단위로 올림하며 최소 1ms다. 보충 한도 초과 후에도 반드시 대기하므로, 매우 높은 레이트에서 통계 처리 중 다음 기한을 지나도 바쁜 반복으로 바뀌지 않는다. 지정한 레이트는 목표값이며 운영체제 스케줄링과 연산 부하에 따라 실제 실행 시각에는 오차가 생긴다. 부하가 지속되면 시뮬레이션 시간이 실제 시간보다 느리게 진행할 수 있다.

취소와 실패:

- 시작 전 취소, 대기 중 취소, 보충 틱 사이의 취소를 처리한다.
- 한 서버 틱을 시작했다면 모든 방의 동기 연산을 마친 후 취소를 처리한다. 이미 실행 중인 `Tick`을 강제로 중단하지 않는다.
- 정상적인 토큰 취소는 `RunAsync`의 정상 종료로 처리한다. 취소와 무관한 예외를 취소로 숨기지 않는다.
- 월드가 예외를 던지면 나머지 방 호출을 중단하고 작업을 실패시킨다. 일부 방만 틱이 증가한 상태가 될 수 있으므로 해당 월드들을 재사용하지 않는다.
- 장시간 반환하지 않는 게임 로직은 종료도 지연시킨다. 종료 시간 상한이나 게임 로직 강제 중단은 제공하지 않는다.

## 4. WorldLoopStatistics — 실행 통계

파일: `src/DeathWish.Server/WorldLoopStatistics.cs`

`internal readonly record struct`로 정의한다. 모든 값의 초기값은 0이며 외부에서 수정할 수 없다.

| 속성 | 타입 | 의미 |
| --- | --- | --- |
| `CompletedTickCount` | `long` | 모든 방의 갱신이 성공한 서버 틱 수. 방 개수만큼 곱하지 않는다. |
| `OverrunCount` | `long` | 모든 방의 갱신에 걸린 시간이 목표 주기를 초과한 서버 틱 수. 대기 복귀가 늦은 횟수와 구분한다. |
| `LastTickDuration` | `TimeSpan` | 마지막 성공 틱의 전체 월드 연산 시간. 대기 시간 제외. |
| `MaxTickDuration` | `TimeSpan` | 성공 틱 중 가장 오래 걸린 전체 월드 연산 시간. |
| `DroppedTime` | `TimeSpan` | 보충 횟수 제한으로 건너뛴 시간의 누계. |

루프가 통계 스냅숏을 일관되게 게시한다. 통계 동기화 구간에서 게임 연산이나 콘솔 출력을 하지 않는다. 매 틱 로그를 출력하지 않으며, 서버 시작 시 레이트를 알리고 종료 시 통계 요약을 출력한다. 연산 실패는 통계와 별도로 예외로 보고한다.

## 5. 기존 클래스 변경

### ServerOptions

- `public const int DefaultTickRate = 30` 추가.
- `public int TickRate { get; }` 추가.
- 생성자 마지막 인자로 `int tickRate = DefaultTickRate` 추가. 기존 호출의 의미를 유지한다.
- `tickRate <= 0`이면 `ArgumentOutOfRangeException`.
- 양의 `int`를 설정값으로 허용한다. 이 검증은 설정 형식 검증이며 해당 레이트를 실제로 달성할 수 있다는 보장은 아니다.

### ServerOptionsLoader

- `SERVER_TICK_RATE`를 정수로 읽어 `ServerOptions`에 전달한다.
- 우선순위는 프로세스 환경변수 → 작업 디렉터리 `.env` → 기본값 30이다.
- 빈 값, 정수가 아닌 값, `int` 범위 초과, 0 이하는 설정 오류다. 유효하지 않은 상위 설정을 하위 기본값으로 대체하지 않는다.
- CLI의 기존 주소·포트 인자는 유지하며 틱 레이트 인자는 추가하지 않는다.
- 시작 시 한 번 읽는다. 변경 후 서버 재시작이 필요하다.
- 구현할 때 `.env.example`과 설정 사용 문서에 `SERVER_TICK_RATE=30`을 추가한다.

### Room

- `public GameWorld World { get; }` 추가.
- 기존 생성자에서 자신의 `RoomId`로 월드를 한 번 생성한다.
- 기존 방 멤버십 관리와 잠금 정책은 유지한다. `Add`/`Remove`에서 `World.Tick`이나 플레이어 상태 변경을 수행하지 않는다.

### RoomManager

- `internal GameWorld[] GetWorlds()` 추가.
- 미리 생성한 방의 월드 참조를 방 ID 오름차순의 새 배열로 반환한다. 호출자가 배열을 바꿔도 관리자의 방 목록은 바뀌지 않는다.
- `GameServer`가 시작 시 한 번 호출하여 루프에 전달한다.
- 실행 중 방 추가·삭제와 월드 교체는 이번 단계에서 지원하지 않는다.

### GameServer

- 생성자에서 `ServerOptions.TickRate`를 저장한다. 공개 생성자는 시스템 시간을 사용하고, internal 생성자 `GameServer(ServerOptions options, TimeProvider timeProvider)`로 테스트에서 제어 시간을 주입한다.
- `RunAsync`마다 별도 월드 목록, 루프, 루프 종료를 제어할 취소 소스와 작업을 소유한다.
- 기존 무한 대기 대신 월드 루프의 완료·실패를 관찰한다.
- 바인딩 성공 후 루프를 시작한다. 바인딩 실패 시 루프를 시작하지 않는다.
- 종료 진입 시 루프 취소를 요청하고 리스너를 닫는다. 루프 완료를 관찰하고 연결 및 이벤트 루프를 정리한다.
- 어느 정리 단계가 실패해도 나머지 자원 정리를 시도한다. 실패가 하나면 원래 예외와 스택을 보존하고, 여럿이면 `AggregateException`으로 전달한다. 취소와 동시에 월드 연산이 실패해도 실패를 숨기지 않는다.
- 기존처럼 자원은 `RunAsync`의 지역 소유로 유지한다. 별도 `Start`/`Stop` API나 실행 중 재설정 API는 추가하지 않는다.

## 6. 검증 및 리뷰 기준

| 대상 | 검증 항목 |
| --- | --- |
| 설정 | 기본 30Hz, 파일·환경변수 우선순위, 잘못된 값, 기존 생성자 및 CLI 사용 호환 |
| 월드 | 방별 독립 인스턴스, 틱 0에서 시작, 완료 시 1 증가, 고정 시간 간격, 잘못된 시간 간격 거부 |
| 스케줄 | 첫 틱 시점, 방 ID 순서, 중복·동시 실행 없음, 작업 시간에 따른 누적 주기 지연 방지 |
| 지연 | 최대 4틱 보충, 초과 시간 건너뛰기, 건너뛴 틱 번호 미증가, 통계 정의와 실제 값 일치 |
| 생명주기 | 시작 전·대기 중·연산 후 취소, 루프 재실행 거부, 연산 실패 전파, 바인딩 실패 시 루프 미시작 |
| 서버 통합 | 실제 TCP 연결이 있는 상태에서 취소 종료, 세션·방 멤버 정리, 포트 재사용, 기존 Echo·방 입장 회귀 검사 |

시간 계산은 제어 가능한 시간 공급자로 검증하고, 실제 시간 기반 실행은 정확한 밀리초 일치 대신 완료·취소·자원 정리를 확인한다. 구현 후 변경 파일, 실행한 검증, 미검증 플랫폼과 부하 한계를 보고하고 Stage 3 리뷰에서 멈춘다. 사용자 승인 전에는 계획의 완료 체크박스를 변경하지 않는다.

## 7. 후속 단계와 한계

- Stage 4에서 네트워크 요청을 명령 큐로 전달하고 월드 루프가 플레이어 상태를 변경하도록 연결한다. 종료 시 퇴장 명령을 모두 처리하는 순서는 그 단계에서 추가로 정의한다.
- Stage 3의 정상 종료는 현재 방 멤버십과 세션 정리를 보장하는 범위이며, 아직 없는 플레이어 상태의 정리까지 구현한 것으로 취급하지 않는다.
- 한 방의 느린 연산은 같은 루프의 다른 방도 지연시킨다. 전용 스레드, 방별 병렬 처리, 부하 분산과 틱 레이트 실시간 변경은 보류한다.
